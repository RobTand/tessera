# Bazel

Bazel runs the merge gate's test population on BuildBuddy, one target per test file and hosted lane (#1589):

- `//tests:test_x` runs `tests/test_x.py` with the CPU torch wheel, like the hosted gate's torch lane.
- `//tests:test_x.bytes` runs it with no torch, like the no-torch lane. A file that needs a package the lane lacks isn't collected, which is what `tests/conftest.py` decides on the hosted gate too.

The hosted gate's own files stay the sources of truth:

- `tools/ci/gate_requirements.txt` and `tools/ci/gate_torch_requirements.txt` pin the packages.
- `tools/ci/gate_quarantine.json` holds the node-level quarantine.
- `tools/ci/gate_budget.json` sets per-test budgets.
- `tools/ci/gate_durations.json` gives per-file times; a file over 40 s is split into Bazel test shards.

## Running tests

Run Bazel on BuildBuddy, never with a local Bazel server on a fleet host. `bb remote` runs the Bazel client on a BuildBuddy runner, mirrors your uncommitted changes, and sends every test to remote execution:

```sh
BUILDBUDDY_API_KEY="$(cat ~/.config/buildbuddy/api_key)" GIT_REPO_DEFAULT_BRANCH=master \
  bb remote \
  --container_image=docker://gcr.io/flame-public/rbe-ubuntu24-04@sha256:5f0c01e5f6d79e58d7a996330de33aa38ce599bf8431eaf27521e7602daadf50 \
  --runner_exec_properties=EstimatedCPU=4 --runner_exec_properties=EstimatedMemory=8GB \
  test //tests:test_alphabet //tests:test_alphabet.bytes --config=remote --jobs=16
```

- **Run targeted tests, not `//...`.** BuildBuddy's executors are shared with the merge gates of TL3, PrismaBuild and PrismaQuant.
- **Read the verdict** from the command's exit status and the invocation it links, not from the start message.
- **Use local Bazel only for short query commands,** with `--max_idle_secs=300` (for example `bazel --max_idle_secs=300 query ...`).

## How the build is generated

Every `BUILD.bazel` except `tools/bazel/BUILD.bazel` is generated by `tools/bazel/build_files.py`, from the dependency evidence in `tools/bazel/evidence.py`. Gazelle can't express Tessera's imports:

- function-local imports join encode, export and the serving stack in cycles;
- tests import other test modules;
- tests put experiment directories on `sys.path`;
- code runs tools and shell scripts by path;
- the packaged `runtime_contract.json` names the modules it loads.

The evidence follows PrismaBuild's rules: real imports only, test paths as data, and path strings counted only where code runs or reads them.

- **One library per module,** and one per import cycle.
- **Data for the files a module reads,** including package data (`pyproject.toml`'s table), which goes on the package's `__init__`.
- **A test target's own inputs:** the programs its code launches, the shell scripts it runs and what they name, and `tools/bazel/test_inputs.bzl`. That table covers reads through a root a caller passes, each with its reason.

A test that reads an undeclared repository file finds it missing on the remote executor and fails; it doesn't pass silently.

The C++ that CPU tests compile at run time (torch's `cpp_extension`, Inductor's CPU kernels) uses the `toolchains_buildbuddy` gcc toolchain, pinned to the executor image. The runner hands its compiler to each test as `CC` and `CXX`. No test in the cloud gate needs CUDA.

## Adding a test file

1. Add `tests/test_<name>.py`.
2. Run `tools/bazel/generate.sh`.
3. Commit the `BUILD.bazel` changes it writes.

The same applies after you add a module or an import, or a fixture a test reads. `tests/test_bazel_build.py` fails when a generated file is stale, when a gate file lacks a target in a lane, or when a target the cloud gate leaves out has no reason.

## Where tests run

Most tests run on BuildBuddy's remote executors. An executor has a few CPUs of a larger host, no network, no `.git`, and every input staged as executable. `tools/bazel/nonhermetic.bzl` names the tests that need more, each with its reason:

- **`runner`:** the test runs on the Remote Bazel runner itself, in its git checkout, which must hold full history. Its result is never cached. The runner is amd64, so the arm64 pass (`--config=remote-arm64`) leaves these out.
- **`gpu`:** every node needs a CUDA device. The target is `manual`, so the cloud gate leaves it out, and a GPU lane selects it by the tag. Its CUDA run stays on PrismaBuild with `--strict-cuda`.
- **`requires-network`:** the remote executor gets a network.

## Configurations

- `--config=remote`: BuildBuddy cache, remote execution on the pinned Ubuntu 24.04 image, and build events.
- `--config=remote-arm64`: the same, on BuildBuddy's linux/arm64 executors.
- `--config=ci`: CI build metadata, a refusal of a stale `MODULE.bazel.lock`, and the per-test receipts that parity reads.

Pass the API key header from the environment or a private rc file. Never commit it.
