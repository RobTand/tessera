## Verdict

The gate (`src/tessera/serving/glm53_nope.py`) now makes two separate
decisions. **Admission** refuses a configuration that is not known to run
correctly, by name. The **eager-equivalence claim** says whether an admitted
configuration runs eager's arithmetic, so that a quality measured on an eager
serve holds for it. Every serve reports the claim once at startup on stderr.

| configuration | admitted | runs eager's arithmetic | evidence (section) |
|---|---|---|---|
| eager (`--enforce-eager`) | yes, any runner | reference | 3 |
| FULL_DECODE_ONLY, every size 1..max captured | yes, backport runner | yes: differences stay inside eager's own run-to-run spread | `fdoN8`, `fdoF8` (2, 4) |
| FULL_DECODE_ONLY, vLLM's default sizes | yes, backport runner | no: padded batches run another reduction order | `fdoF1`, `fdoN2` (4) |
| PIECEWISE or FULL_AND_PIECEWISE, every size captured | yes, backport runner | yes | `pwN2`, `fapN8` (6) |
| PIECEWISE, default sizes | yes, backport runner | no | `pwN1` (6) |
| VLLM_COMPILE, graph NONE, `custom_ops ["all"]`, IR ops `vllm_c` first | yes | yes | `cnoneV2` (5) |
| VLLM_COMPILE with vLLM's default op settings | yes (NONE or FULL_DECODE_ONLY) | no: it switches op implementations | `cnoneA1`, `cnoneV1`, `cfdoA1` (5) |
| VLLM_COMPILE with PIECEWISE, FULL_AND_PIECEWISE or split FULL | refused: needs the breakable graph, which forces mode NONE | | 5 |
| DYNAMO_TRACE_ONCE, graph NONE | yes | no (default ops) | `cdtoA1` (5) |
| DYNAMO_TRACE_ONCE with graphs | refused: measured without graphs only | | |
| STOCK_TORCH_COMPILE | refused: fails to start (Dynamo) | | |
| any graph mode on the stock runner | refused: the kpool-tail read (vllm-project/vllm#57317) | | 1 |
| any graph mode with a speculative config | refused: no drafter graph path is measured | | 9 |

The padded-graph divergence is a **capture-size policy**, not a kernel
determinism fix: the op that separates a padded replay from eager, vLLM's mHC
fused post/pre op, is repeat-exact at every token count, and a padded replay
runs it at the padded count, which selects another split-K and so a valid,
different fp32 reduction order (section 4).
Capturing every size from 1 to the largest makes graph and eager run the same
arithmetic, at a measured cost of one small graph per added size (section 7).

## 1. The chunk-2 illegal memory access: cause and fix

**Cause.** The stock V2 runner computes a generic slot mapping for every KV
group that is not a `CircularBufferSpec`, the kpool tail included
(`model_runner.py`, `slot_mapping_enabled`). The mapping kernel
(`block_table.py:339-347`, `_compute_slot_mappings_kernel`) loads
`block_table[req, position // block_size]` with no bound on the column: the
load's mask is the context-parallel `is_local`, which is `True` at CP size 1.
The kpool tail has one 4-token circular block per request in a row 32
entries wide, and the stub's tail table is 8 x 32 int32 = 1 KiB. Position 128
already reads past its row and position 1024 past the table. A two-chunk
3649-token prefill reads up to entry 912. Whether that read faults depends on
what is mapped after the table. That is consistent with #581 (image
`a5424378`): it saw the illegal memory access in 6 of 10 FULL_DECODE_ONLY
serves, 2 of 2 PIECEWISE ones and none of 7 eager ones, and its
`CUDA_LAUNCH_BLOCKING=1` run raised it in this kernel, launched from
`prepare_attn`.

**The read, measured at the kernel.** `kpool_tail_slotmap_repro.py` builds the
stub's block-table geometry in the stock image, the tail table as its own
allocation, and runs the stock kernel under the CUDA memcheck tool
(PrismaBuild action `1894e264`, sparky, receipts
`/mnt/shared/tessera-runs/receipts/508-graphs-20260928/unit-f8dbe1a0-r2`):

| rule | memcheck errors | first invalid read | run |
|---|---|---|---|
| stock (tail mapped) | 98 (50 printed), all in program (1,0,0), the tail group | `block_table.py:344`, 0x420 B past the tail table = flat entry 264 = position 1056 (entries 256-263 land in the 32-byte allocation after it) | kernel aborted, `unspecified launch failure` |
| tail opted out | 0 | none | clean |

**The tail's slots, checked, not only bounded.** The values the generic
kernel computes for the tail are wrong (`generic_tail_equals_expected:
false`), and they are never used: `KpoolTailMetadataBuilder` overwrites the
tail row with `block_table[req, 0] * 4 + position % 4` whenever the common
metadata carries positions, which the default and mamba-hybrid model states
pass. Under both rules the slots written are exactly the expected ones
(`written_tail_equals_expected: true`, for example `28, 29, 30, 31, 28, 29`
for the request in block 7). The fix is therefore the upstream one,
vllm-project/vllm#57317 (70df48dc3d01, `KpoolTailSpec.uses_slot_mapping = False`): the runner
stops mapping the tail at all, instead of masking a read whose result is
discarded. The backport image carries it as a two-line edit to the runner.

**Drafter caveat.** vLLM's speculator builds attention metadata without
positions (upstream too), so a drafter's tail row keeps the runner's mapping:
before the backport that was the out-of-bounds generic row, after it the pad
slot. The stub has no MTP layer, so drafter acceptance on the backport image
is not measured here, and the gate refuses graph mode with a speculative
config.

**In a serve.** On the backport image in FULL_DECODE_ONLY, 19 two-chunk
3649-token prefills (2048 + 1601 tokens) across four serves completed with no
illegal memory access or CUDA error in any serve log: `fdoN8` 10, `fdoN2` 4,
`fdoN1` 3, `fdoNmc3` 2; `fdoP1` served five more in its latency probe.
`fdoNmc3` ran the whole serve under `compute-sanitizer --tool memcheck` on
the mapping kernel: 0 memory-access errors. Its summary counts 13 errors, all
`CUDA_ERROR_INVALID_VALUE` on `cuGetProcAddress_v2` from cuda-python's driver
symbol probing at import, none on a kernel. That run alone cannot tell the
two runners apart: the same probe on the stock image (`memSn3`, eager) also
reports 0 access errors, because in a serve the tail table is a
sub-allocation of PyTorch's caching-allocator segment and the overrun stays
inside it.

A serve pair does separate them once the table is its own allocation. Both
arms below ran eager with `PYTORCH_NO_CUDA_MEMORY_CACHING=1` under
`compute-sanitizer --tool memcheck --padding 8192 --kernel-name
kns=_compute_slot_mappings_kernel`, and sent one 3649-token prompt:

| arm | image | memcheck on the mapping kernel | the 3649-token prefill |
|---|---|---|---|
| `memSn4` | stock `f8dbe1a0` | 128 invalid 4-byte reads at `block_table.py:344`, all in program (1,0,0), the tail group; each lands 129 to 253 bytes past a 1024-byte allocation (the 8 x 32 int32 tail table), so flat entries 288 to 319 | the kernel aborts; the engine core dies with `CUDA error: unspecified launch failure` at the next CUDA call (the indexer's prefill-chunk `cumsum`) |
| `memNn4` | backport `c2e75e03` | 0 access errors (the summary's 13 are the `cuGetProcAddress_v2` probes) | completed; 8 tokens generated, no CUDA error in the serve log |

The flagged entries 288 to 319 hold positions below 1280 for any request row
(`row * 32 + position // 4`), so the stock runner reads past the table
already in the first 2048-token chunk, and it does so in eager. "Chunk 2" is
where #581's graph serves happened to fault under the caching allocator's
layout, not where the out-of-bounds read begins. The stock eager path makes
the same read; eager serves have not faulted because the read lands inside
the allocator's segment, and the values are discarded, not because it is in
bounds. The backport removes the read in both modes.

## 2. Protocol: the equality suite and the membership criterion

**The suite.** `equal-508.py` sends greedy requests with the top 20 logprobs
of every generated token (32 tokens each): at batch 1 with prompt lengths 1,
2, 5, 8, 17, 100, 500, 1500 and 2000; at batches 2 to 8; and two pairs of
repeated batch-1 requests (`rep_len1_*`, `rep_len17_*`); 48 completions in
all. Every case keeps prompt plus generated tokens at or under 2048 (section
3). A batch is one completions request admitted under `POST /pause?mode=keep`
and released by `/resume`, so its prompts enter the same engine step (every
arm below records `"_admission": "paused"`). `eq2` repeats the whole suite
later in the same serve (the `-r2` receipts).

**Eager is not repeat-exact** (section 3), so a graph arm is compared with the
set of outcomes eager produces, not with one eager serve.
`eq-member-508.py` calls a graph completion a member when its generated token
ids and all 32 top-20 logprob lists are bit-identical to the same completion
of some eager run in a pool of paused-admission eager serves (both passes of
each). Cases that send the same batch (the same prompt token ids and
generation length) share one outcome pool. For a non-member the tool names the
nearest eager outcome and the largest logprob difference **on an identical
prefix**: over the positions up to and including the first differing token
id, where both runs condition on the same tokens. The pool is a sample, so
membership is a lower bound on agreement.

**The magnitude check.** For a pair of runs, `table` below also reports the
largest *logit* change on an identical prefix: at each position, every shared
top-20 token's logprob moves by its logit change minus the log-normalizer
change, and the most common move is the normalizer alone, so subtracting it
recovers each logit's change.

## 3. Eager's own variation, and what "equal" can mean

Eager serves of the same image, the same requests, in the same order, differ
(`table`, deterministic MoE finalize in the `F` arms, stock finalize in `N`,
`S`, `digEE3`):

| pair (both eager) | completions differing | changed a generated token | largest logit change | largest logprob change |
|---|---|---|---|---|
| `eagerF2` vs `eagerF1` (fresh serves) | 4/48 | 0 | 0.09375 | 0.09473 |
| `eagerF1` pass 2 vs pass 1 | 4/48 | 1 | 0.12500 | 0.09845 |
| `eagerN2` pass 2 vs pass 1 | 8/48 | 1 | 0.21875 | 0.18732 |
| `eagerS2` (stock image) vs `eagerN2` | 6/48 | 0 | 0.21875 | 0.18732 |
| `digEF3` pass 2 vs pass 1 | 3/48 | 1 | 0.06250 | 0.06370 |
| `digEE3` pass 2 vs pass 1 | 6/48 | 1 | 0.06250 | 0.06311 |

**Every eager difference starts as one bf16 rounding step of a few logits.**
At the first position where two eager runs' top-20 lists differ, 0 to 5
tokens' logits moved (0 means a logit outside the top 20 moved), and every
one moved by exactly 2^-5 = 0.03125 or 2^-4 = 0.0625 nats: the spacing of
bf16 at magnitudes [4, 8) and [8, 16). The logits leave the model in bf16, so
this is the smallest visible difference: an upstream change of any size that
crosses one bf16 rounding boundary. No other size occurs at any differing
completion of the eager pairs above. Later positions compound a few such
steps, to at most 0.21875 nats on a logit in these serves.

**Where it starts** (per-module digests, `T508_DIGEST_FULL=1`, the two passes
of one serve forward by forward, a forward counted only when its input token
ids match):

- **The MoE experts module of layer 1.** Its output differs while its input
  matches. With FlashInfer's fused finalize (atomics; FlashInfer's docstring
  says run to run nondeterministic) `digEE3` shows 6 such forwards, including
  a 2000-token prefill. Forcing `use_fused_finalize=False` on every call
  (`T508_MOE_DETERMINISTIC=1`, `digEF3`) leaves every prefill identical
  across passes (14 prefill pairs) and 2 decode forwards (3 and 4 tokens) that
  still differ at the same module. The remaining source is inside that module
  and is not placed below it.
- **KDA on a one-token prompt.** A prompt of one token is classified as a
  decode (`gdn_attn.py:251`, `decode_threshold=1`), and its first forward's
  layer-0 KDA output depends on what the engine served before (`digEE1`:
  three sequential repeats of one 1-token request differ at
  `layers.0.self_attn` with identical input; 17- and 2000-token repeats are
  identical). This is stock vLLM behavior, tracked separately.
- The KDA layer 2 outputs that differ after either event carry the difference
  in their recurrent state; they are not new origins.
- **Above 2048 tokens** the stock top-k kernel writes its selection in arrival
  order (`sampler.cu:267`, an `atomicAdd` slot counter; #581 finding 1), so the
  3649-token prefills are not repeat-exact (`fdoN8`: first-token logprob
  -4.72 to -4.92 over 10 repeats). All equality claims here are restricted to
  requests of at most 2048 tokens; the long prefills answer the memory-safety
  question only. Making that kernel deterministic is not attempted.

So on this stub "graph runs eager's arithmetic" is tested as: every graph
completion is an eager outcome, and where it is not, the difference has the
signature and size of eager's own variation.

## 4. Padding: the mechanism, and why the fix is a capture-size policy

**Mechanism.** vLLM's V2 runner (`cudagraph_utils._init_candidates`) runs a
batch of n tokens in the smallest captured graph of at least n tokens, so
with vLLM's default sizes `[1, 2, 4, 8, ...]` a decode batch of 3, 5, 6 or 7
requests runs every op at 4 or 8 rows. Most ops compute each row
independently, but vLLM's mHC TileLang op picks its split-K reduction from the
token count (`model_executor/kernels/mhc/tilelang.py:518-522`,
`mhc_fused_post_pre_tilelang`):

```python
if num_tokens <= 16:                        # small-FMA path
    tile_n = 2 if num_tokens < 8 else 3
    n_splits = 8 if (num_tokens < 8 and hidden_size <= 4096) else 4
else:
    n_splits = compute_num_split(64, K, cdiv(num_tokens, 64))
```

**At the op** (`mhc_split_repro.py`, layer 1's real `hc_attn_*` tensors,
seeded activations, receipt `serve-arms/mhc-split/mhc_split.json`): for each
pair (m rows, p >= m rows with the same first m rows), the first m rows of
every output are compared bit for bit. Every size is repeat-exact.

| m -> p | configuration (tile_n / splits) | first m rows |
|---|---|---|
| 1->2, 2->4, 3->4, 4->4 | 2/8 -> 2/8 | identical |
| 5->8, 6->8, 7->8 | 2/8 -> 3/4 | differ: `post_mix_cur` 4-5 elements (max 6.0e-8), `comb_mix_cur` 21-23 elements (7.0e-10) |
| 8->16, 9->16, 12->16, 16->16 | 3/4 -> 3/4 | identical |
| 13->24 | 3/4 -> 48 splits | differ: `layer_input_cur` 806 elements (max 4.9e-4) |
| 17->24, 24->32, 40->48 | 48 -> 48 | identical |
| 60->72 | 48 -> 24 | differ |

`mhc_pre_tilelang` is identical up to 64 tokens and differs from 64 to 72.
The classes {1..7}, {8..16}, {17..64} and so on reduce in different orders.

**Served** (`fdoF1`: FULL_DECODE_ONLY with vLLM's default sizes `[1, 2, 4, 8]`;
`fdoF8`: every size 1 to 8; both against `eagerF1`, deterministic finalize in
all three):

| batch | padded to | `fdoF1` differing | changed a token | largest logit change | largest logprob change | `fdoF8` differing |
|---|---|---|---|---|---|---|
| 2, 3, 8 | not padded | 0 | 0 | 0 | 0 | 0 |
| 4 | not padded | 1/4 | 0 | 0.03125 | 0.06188 | 0/4 |
| 5 | 8 | 5/5 | 2 | 0.31250 | 0.98081 | 1/5 (0.03125, 0.06212) |
| 6 | 8 | 6/6 | 1 | 0.56250 | 0.69582 | 0/6 |
| 7 | 8 | 7/7 | 2 | 1.00000 | 0.96758 | 1/7 (0.03125, 0.09473) |

(the per-batch logit column is the change at each completion's first
differing position; whole-completion maxima are in the table of section 6).
Each padded batch moves every completion, up to 17 of the top-20 logits at
the first difference and by up to 1.0 nats; the batch 4 difference and
the two `fdoF8` differences are one-step eager-class changes (section 3). The
same 0.98081 appears in `fdoN2` on the other finalize, so the padded result is
itself deterministic: a different computation, not noise. A fp32 difference
of 1e-8 to 1e-4 in the mixing coefficients grows to about one nat through the
remaining layers; which op amplifies it (for example a routing near-tie) is
not measured.

**Verdict.** Capture-size policy. The TileLang kernels are deterministic at
every size; the divergence is replaying a size that is not the batch's own.
Capturing every size from 1 to the largest removes it (sections 2 and 6),
and a padded configuration stays admitted but is not claimed equal to eager:
its quality must be measured on it (served KL against BF16) rather than
inherited from eager.

## 5. Compilation: VLLM_COMPILE switches op implementations and compiles nothing

With `VLLM_USE_BREAKABLE_CUDAGRAPH=0` vLLM starts in VLLM_COMPILE and logs
``torch.compile` is turned on, but the model ... does not support it``
(`vllm.py:2989`); no graph is compiled. The mode still changes two defaults:
`custom_ops` becomes `["none"]` instead of `["all"]`, and the IR op priority
of `rms_norm` and `fused_add_rms_norm` becomes `["native"]` instead of
`["vllm_c", "native"]`. Each switch alone moves all 48 completions outside
eager's outcomes (pool: `eagerN2`, `eagerS2`, `digEE3`, both passes each; the
gate quotes the same figures):

| arm | differs from eager in | non-members | changed a token | largest logprob change (nearest outcome) |
|---|---|---|---|---|
| `cnoneV1` | `custom_ops ["none"]` | 48/48 | 25 | 1.0608 |
| `cnoneA1` | IR ops `native` | 48/48 | 9 | 0.0644 (one bf16 step at the first difference) |
| `cdtoA1` | DYNAMO_TRACE_ONCE, both defaults | 48/48 | 25 | 1.0510 |
| `cfdoA1` | IR ops `native`, FULL_DECODE_ONLY, default sizes | 48/48 | 13 | 0.9791 |
| `cnoneV2` | nothing (`custom_ops ["all"]`, IR ops `vllm_c` first) | 1/48; 0/48 against every eager serve | 0 | 0.0317 (one bf16 step) |

The native RMSNorm composite rounds differently from the `vllm_c` kernel, so
`cnoneA1` shifts single logits by one bf16 step on nearly every completion;
the `none` custom ops swap in composite implementations of larger ops, and
move logits by up to 1.28 nats. The gate names the switch that differs and
withholds the equivalence claim; it does not refuse the mode. VLLM_COMPILE
with PIECEWISE, FULL_AND_PIECEWISE or a split FULL graph is refused: those
need the breakable graph, and with it off vLLM refuses to start them.

## 7. Capture pricing

`T508_CAPTURE_LOG` wraps the V2 runner's `CudaGraphManager.capture` and
records, per graph, the wall time of its warmup plus capture and the change in
the caching allocator's reserved bytes (the graph pool), between device
syncs. Stub, FULL_DECODE_ONLY, backport image:

| max_num_seqs N | sizes captured | graphs | capture wall | graph-pool reserved | per-graph wall |
|---|---|---|---|---|---|
| 4 (the release value) | default `[1, 2, 4]` | 3 | 12.450 s | 466.0 MiB | 4: 12.155, 2: 0.021, 1: 0.271 |
| 4 | every size `[1..4]` | 4 | 12.756 s | 466.0 MiB | 4: 12.407, 3: 0.022, 2: 0.020, 1: 0.304 |
| 8 (the stub value) | default `[1, 2, 4, 8]` | 4 | 18.583 s | 490.0 MiB | 8: 12.647, 4: 5.594, 2: 0.042, 1: 0.297 |
| 8 | every size `[1..8]` | 8 | 18.583 s | 490.0 MiB | 8: 12.562, 7: 5.589, 6-2: 0.022-0.030 each, 1: 0.308 |

An added size costs 0.02 to 0.03 s of capture and no graph-pool memory: vLLM
captures the largest graph first and the smaller ones reuse its pool (each
adds about 1 KiB of allocated bytes). The first graph's 12 s and the first
graph under 8 tokens (5.6 s) are one-time costs that the default list pays
too; the second is consistent with compiling the kernels that change
configuration at 8 tokens, such as the mHC op's `tile_n = 2` variant, but it
is not profiled. So N = 4 adds one graph for about 0.02 s, and N = 8 adds
four for about 0.1 s. Driver-side graph instantiation memory is outside the
caching allocator and is not isolated here. vLLM's own "took X GiB" line read 1.20, 0.83, 1.13 and 0.72 GiB for
these four serves: it is the drop in device free memory, which on GB10's
unified memory moves with the page cache, so it does not grow with the graph
count and cannot price a graph. On the 45-layer model an added graph captures
about 11 times the kernels; that wall time is estimated, not measured.

Netdata's `nvidia_smi.gpu_power_draw` (10 s resolution) agrees: 37 to 44 W in
the decode windows, 53 to 74 W across the prefill cases; the box's CPU was 7
to 10% busy (`system.cpu`), so nothing else loaded it.

The graph removes 8.5 ms of host work per step, but on the stub that work was
already hidden: the GPU is busy 97% of the step in eager, in large

energy per token by 3%. The effect on the 45-layer model, whose host and
device work per step both grow, is not measured here.

## 9. What the full-model TP2 graph serve needs

Not run: the full GLM-5.3 model needs both Sparks at TP2 (45 layers plus
MTP). Its requirements:

- Image `c2e75e03` (the backport runner), `TESSERA_RESEARCH_GLM53_NOPE=1`, and
  `--compilation-config '{"cudagraph_mode": "FULL_DECODE_ONLY",
  "cudagraph_capture_sizes": [1, 2, ..., max_num_seqs]}'` (or
  FULL_AND_PIECEWISE with every size to the largest prefill size captured),
  so the serve reports that it runs eager's arithmetic.
- The release configuration (`max_num_seqs 4`, dflash k=7 with MTP 2 as
  rollback) is refused today: no drafter graph path is measured. It needs a
  drafter graph receipt, with every multiple of `1 + k` up to `4 (1 + k)`
  captured. Whether padding changes the arithmetic at those sizes is not
  measured (24 and 32 tokens share an mHC class, but other kernels choose by
  token count).
- The equality suite against a TP2 eager serve with the membership
  criterion, at least 10 two-chunk prefills, a check that sequence-parallel
  padding does not reintroduce padded replays, graph memory and capture wall
  from `T508_CAPTURE_LOG`, a route census, and the section 8 profile on the
  full model.
- `TESSERA_ROUTE_TRACE` is eager-only by design (`serving/telemetry.py`,
  tessera#102): it does not count FULL_DECODE_ONLY decode replays, so a route
  trace of a graph serve under-reports decode. A consumer that compares a
  trace with an artifact's priced routes must know which mode served it.

## 10. Limitations

- One four-layer stub at TP1. The mechanism is general (the mHC op and the
  runner dispatch are the full model's), but the magnitudes are the stub's.
- Membership is a lower bound: each eager pool holds 4 to 12 sampled runs
  (both passes of 2 to 6 serves).
- Eager's residual variation under the non-fused finalize is placed at the
  MoE module of layer 1, not below it.
- The eager-equivalence claim is a startup log line; no machine-readable
  carrier exists yet for a consumer to gate on.
- FULL_DECODE_ONLY digests cover eager forwards only; per-module comparison
  of replayed decode steps was not made.
